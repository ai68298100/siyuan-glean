# 阅读体验与 RSS 阅读器交互调研

> 调研日期：2026-09-29。本文补充 `docs/RESEARCH-folo.md`，重点核对“剪藏全文怎样读、怎样摘录、怎样调用 AI”这条使用链。引用均为产品官方文档或官方博客；本文记录的是可吸收的交互原则，不代表小驴拾遗已经实现。

## 1. 核对范围与官方证据

### Readwise Reader

- [Long-form reading](https://docs.readwise.io/reader/guides/workflows/longform-reading)：提供专门的长文阅读布局，隐藏操作密集的底栏，突出阅读进度和外观设置；支持分页滚动、两端对齐，并可把“当前正在读”设为默认入口。
- [Navigation FAQ](https://docs.readwise.io/reader/docs/faqs/navigation)：阅读页支持自动前进设置；网页端以 `Cmd/Ctrl + K` 打开命令面板，`?` 查看快捷键，快捷键可以自定义；侧栏可按偏好默认隐藏。
- [Highlights, Tags, and Notes FAQ](https://docs.readwise.io/reader/docs/faqs/highlights-tags-notes)：上下方向键逐段移动焦点，`H` 高亮、`T` 加标签、`N` 加笔记；自动高亮可以关闭；原网页高亮器作为解析不完整时的补救路径。
- [Ghostreader overview](https://docs.readwise.io/reader/guides/ghostreader/overview)：同一套 AI 入口支持全文或选中文本；`G` 针对选择、`Shift + G` 针对全文；预置 prompt 可总结、解释、翻译，回答留在阅读上下文中。
- [Quick Lookup](https://docs.readwise.io/reader/guides/ghostreader/quick-lookup)：移动端选择 1–3 个词后出现 Define / Lookup / Translate；结果默认只临时显示，可复制，或把结果随选中文本保存为高亮批注。
- [Parsing FAQ](https://docs.readwise.io/reader/docs/faqs/parsing)：保存时保留当时解析出的版本，不因原文后来变化而悄悄重解析；解析缺失时可以打开原文并重新保存；重复 URL 会被识别，但带跟踪参数的不同 URL 仍可能重复。
- [Filtered Views FAQ](https://docs.readwise.io/reader/docs/faqs/filtered-views)：用标签、来源、作者和查询建立可保存、可固定的筛选视图，而不是为每个视图复制一份状态。

### Inoreader

- [Inoreader Intelligence and article summaries](https://www.inoreader.com/blog/2025/03/inoreader-intelligence-and-article-summaries-are-here.html)：文章标题下提供 `Summarize`；一次点击运行通用摘要，箭头打开其他 prompt，也可以输入自定义问题。结果直接显示在文章内，可查看 prompt、复制或删除，并进入站内搜索。偏好设置可调整按钮位置、persona、摘要语言及 prompt 顺序。官方明确说 AI 不过滤或改变 feeds，用户决定何时使用。
- [New rule triggers and actions](https://www.inoreader.com/blog/2025/10/introducing-new-rule-triggers-and-actions-translations-summaries-and-more.html)：规则动作包括摘要、翻译、添加笔记等，并建议只对预筛选内容做自动翻译；这是自动化能力的证据，不等于适合默认自动代读。

## 2. 对现有产品与原型的复核

`design/prototype.html` 和 `docs/UI-STANDARD.md` 已把列表、网格、看板、状态色和批量操作做得较完整，但主要解决“管理读库”。`docs/PRODUCT-REPLAN.md` 已规定全文优先、仅链接明确提示、开始阅读与读完分离；当前仍缺一层“读文章时怎么操作”的明确界面协议：

1. 列表卡点击后直接进入思源文档，缺少阅读载体、来源切换和当前阅读上下文的统一说明。
2. 高亮视图能聚合引述和制卡，但没有规定从正文选中文本到摘录、批注、制卡的连续路径，也没有把 AI 的上下文范围说清楚。
3. `reading` 只表达队列状态；如果加入进度、断点或自动下一篇，必须先定义持久化含义，不能把打开、滚动或 AI 生成结果推断成 `done`。
4. 桌面原型已有阅读中进度条示意，但数据契约尚未提供可信的阅读位置字段；示意不能直接变成伪精确的百分比。
5. 现有 AI 预置动作是文档级入口，尚未区分“针对全文”和“针对选中文本”，也没有统一结果的来源标记、复制/保存入口和额度提示。

## 3. 可吸收的产品原则

### 3.1 把管理视图与聚焦阅读分层

列表、网格和看板负责找文章及改状态；打开全文后进入低干扰阅读上下文，顶部只保留标题、载体徽章、来源动作、当前状态和一个明确的完成入口。正文阅读不应被批量操作条或统计信息打断。桌面可以保留可收起的 AI/摘录侧栏，移动端用底部动作 sheet；两者都必须能回到正文。

### 3.2 明确正文、原文和本地文档的切换

每篇条目在打开前就显示 `全文`、`仅链接` 或 `本地文档`。全文优先打开思源正文，并提供“打开原文”作为次级动作；仅链接直接说明“需要打开来源网页”；本地文档不显示网页动作。原文打开不能改变五态，也不能因为网页打开成功就写 `done`。

### 3.3 让“下一篇”成为显式的队列动作

读完后可以选择“标记读完并打开下一篇”，或只标记读完返回队列。默认不自动前进；若日后提供自动前进开关，必须在用户已经明确标记完成后才推进，且下一篇的打开失败不能回滚上一篇的完成记录。略过、返回和关闭都不改变完成历史。

### 3.4 摘录先保存用户选择，再调用 AI

最小路径是：选中文本 → `摘录`（保留原文、文档 ID、块定位和时间）→ 可选“加笔记 / 制卡 / 让 AI 解释或翻译”。AI 结果默认临时显示，用户选择复制或保存后才写入文档；保存的 AI 内容要带来源标记和动作名，不能混入用户标签或冒充正文。无法取得块定位时，界面要提示“仅复制文本”，不伪造锚点。

### 3.5 AI 按上下文分级、手动触发

阅读页至少区分三种上下文：选中文本、当前文档、相关旧文集合。摘要、翻译、提问、相关旧文分别显示动作和预计成本；没有模型、超过额度或失败时保留正文和摘录入口。Inoreader 的“文章内按钮 + prompt 下拉 + 自定义问题”可以借鉴为紧凑入口，Readwise 的“选区/全文快捷键”可以借鉴为上下文边界。继续保持本插件不做通用聊天窗、不自动代读。

### 3.6 解析质量要可解释

全文是保存时的快照；原网页变化不应静默覆盖思源正文。若正文缺段、图片或表格，阅读页应给出“打开原文”和“反馈/重新剪藏”的明确动作，记录缺失原因；重新剪藏属于用户显式动作，并按收录管线处理。来源 URL、快照时间和载体类型要与正文并列显示。

### 3.7 快捷键只做低风险动作

先提供可发现、可自定义的命令面板动作：打开阅读、打开原文、摘录选区、标记读完、稍后读、归档、下一篇。快捷键不直接执行不可逆批量操作；移动端用同一组动作的按钮或手势。`?` 显示帮助，命令面板是无障碍和非标准键盘布局的回退入口。

## 4. 不直接照搬的部分

- 不引入 RSS 订阅、云端阅读库、账号同步、社交集合或付费 AI 配额；小驴拾遗的事实源仍是思源文档属性。
- 不把 Readwise 的段落焦点、自动高亮、分页滚动当成现成思源 API；先做真机能力探测和最小交互，再决定是否实现。
- 不复制 Inoreader 的规则自动摘要/翻译作为默认路径。若未来开放自动动作，必须按现有 `enrichMode`、每日额度、失败静默和来源标记单独验收。
- 不新增“阅读百分比”或“断点”字段，除非先在 `docs/DATA-CONTRACT.md` 定义来源、更新时机、跨设备冲突和归档关系。

## 5. 建议的验收样例

用一篇有正文、一篇仅链接、一篇无来源本地文档和一篇正文不完整的剪藏逐项走查：

1. 四种载体的徽章和打开动作正确；打开原文不改变状态。
2. 开始阅读只进入 `reading`；关闭、返回、略过不写 `done`；显式读完后才可下一篇。
3. 选中一段文字可复制、摘录、制卡；摘录保留文档和块定位，定位失败时有明确降级。
4. AI 选区动作只把选区送入请求，全文动作才读取全文；结果可复制或保存，失败不影响正文。
5. 重新打开同一篇文章时，管理视图的筛选、状态和载体与阅读页一致；索引重建不产生新的状态。
6. 桌面宽屏、Dock 和移动端都能找到同一组低风险动作；命令面板和 `?` 帮助可达。

这些样例仍需隔离内核验证和作者真机走查，完成前不写入 README 的能力承诺。
