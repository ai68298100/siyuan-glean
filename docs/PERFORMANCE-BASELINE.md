# 大库性能基线

T-3206 用合成数据复现扫描、索引重建、筛选/分面、导入解析和今日拾遗的主要计算链路。它测量真实服务函数与纯函数，报告写入 `output/performance/last-run.json`，避免把一次机器上的毫秒数伪装成跨设备承诺。

## 运行

```text
pnpm perf:baseline
pnpm perf:check
```

测试规模固定为 1,000、5,000、10,000 条。扫描使用真实 `scanDocScopes`，按当前 500 条分页；重建使用真实 `reconcileIndex`，按当前 200 个 ID 一批读取属性并经过 `saveData` 序列化；筛选、分面、导入 CSV 解析和今日拾遗直接调用生产纯函数。

`perf:check` 检查五类操作的中位耗时预算、扫描结果数量、查询分页上界、属性批次上界、导入条目完整性和今日拾遗数量。当前预算是本地合成基线的回归护栏，不是作者机器的用户体验承诺；出现超预算时先确认环境负载，再定位算法、分页或序列化退化。

读库面板先渲染已有派生索引，再继续完整属性对账，降低首屏等待期间的空白；同一插件实例同时触发的对账共享一次扫描。对没有状态、URL、标签等快速证据的笔记，Markdown 模板检查限制为4路并发，以减少逐篇串行请求的等待，同时保留完整覆盖。真实宿主的大库卡顿仍需在作者数据规模和设备上测量，Node 合成基线不能替代该测量。

## 结果解释

- 扫描查询预算是 `3 × (ceil(规模 / 500) + 1)`：全库状态/URL、锚点笔记本和 #剪藏 标签三类范围各自允许最后一次空页。
- 属性批次预算是 `ceil(规模 / 200)`，对应 `batchGetBlockAttrs` 的当前批量边界。
- `saveData` 只保存派生索引；基线检查索引条目数量和序列化路径，不把文档属性复制成另一份真相。
- 过滤和今日拾遗测量生产纯函数；UI 首屏、列表滚动、移动端触控和长文切换必须在真实思源宿主中另测，不能用 Node 基线替代，归入 B-0002。
- 外部 Pocket/Omnivore/wallabag 文件和真实内核导入速度还需要作者用实际导出文件核对；本基线只锁定解析计算和大批量输入退化。
