# 反馈闭环

这份记录规范把一个问题从发现推进到修复和验证。它补充 Issue、Pull Request 和作者真实验收手册；它不把代码通过、隔离测试或浏览器窄视口截图当作真实宿主或真机完成。

## 1. 发现

先使用对应的 GitHub Issue 模板：问题报告、功能建议或使用问题。问题报告至少写清：

- 插件版本、思源版本、前端类型和文章载体（全文、仅链接、本地文档、候选或不确定）；
- 首次出现版本；如果知道，补充最后一个正常版本；
- 在真实思源宿主中的操作步骤、期望结果和实际结果；
- 是否可以重现、是否影响已有文章属性或派生索引；
- 截图、录屏或日志。分享前移除标题、URL、正文、路径、令牌和模型地址等敏感内容。

如果问题涉及断网、权限、批量部分失败或异步结果，记录第一次失败后的重试步骤、重试结果，以及仍失败时保留的状态。能力边界和已知阻塞先查阅[能力矩阵](CAPABILITY-MATRIX.md)、[恢复矩阵](RECOVERY-MATRIX.md)和[阻塞清单](BLOCKERS.md)。

## 2. 诊断

维护者在 Issue 中补充：归属（产品缺陷、文档问题、环境问题或功能建议）、影响（数据、状态动作、阅读路径、视觉、性能或安全）、最小复现、证据和是否受 B-xxx 阻塞。

涉及 `custom-clip-*`、存储、内核端点、迁移或恢复时，先核对[数据契约](DATA-CONTRACT.md)和[架构决策](DECISIONS.md)。未有真实证据时，状态写成“待验证”或“阻塞”，不要写成“已修复”。

## 3. 修复

修复 PR 的正文引用 Issue，并说明用户可见结果、影响范围、数据契约/i18n/平台变化、失败与重试语义、用户已有字段保护、验证命令和仍待真实验收的 blocker。

PR 合并前至少运行 `pnpm check`、`pnpm test`、`pnpm build`、`pnpm visual:check`、`pnpm check:release`；涉及任务板时还要运行 `pnpm task:ledger -- --check`。安全问题按 [SECURITY.md](../SECURITY.md) 私密报告。

## 4. 验证与关闭

| 结果 | 关闭条件 |
| --- | --- |
| `fixed-verified` | 修复提交、自动化结果和可复现步骤齐全；若任务要求真实宿主/真机，还必须有对应设备证据 |
| `fixed-isolated` | 代码和隔离验证通过，但真实宿主、真机、模型或外部文件仍待作者验收 |
| `blocked` | 已明确缺少设备、模型、订阅、真实文件或作者操作，并链接对应 B-xxx |
| `wont-fix` | 记录原因、替代路径和对用户的影响 |

真实验收记录使用[作者验收手册](ACCEPTANCE.md)的格式：验收项编号、设备/环境、步骤、预期、实际、截图或录屏、结果和日期。
